# HID-USB-20261006 — Powered Lightning adapter and Pico mouse smoke test

Status: Pico flashed and USB mouse operation verified on the rig. XR2's WDA and
recording-cleanup connection did not survive USB removal. Adapter acceptance
awaits a recorded test after resolving that transport dependency. No collection
or training.

## Scope and physical setup

The operator acquired a camera-style adapter with male Lightning to XR2, female
Lightning to the powered USB board via its charging cable, and USB-A to the Pico.
The operator confirmed XR2 is charging and Wi-Fi is enabled. Charging is evidence
for the phone's power path, not USB mouse enumeration or sustained load capacity.

The Pico had unknown firmware from about two years earlier and no jumper-wire
connection to the ESP32; the ESP32 was disconnected. No host command path to the
phone-attached Pico existed. The operator then disconnected both XRs from the rig,
connected the Pico to the rig and explicitly requested that its old firmware not
be preserved. No firmware backup was made.

## Firmware and rig verification

- Device: first-generation Pico, RP2040 B2, 2 MiB flash, unique flash ID
  `E660C0D1C73D5A2B`. Existing SDK metadata named board `pico`.
- New source: [bounded mouse smoke test](../../hardware/pico_mouse_smoke/README.md).
  Arduino-Pico 6.2.0 with its included Adafruit TinyUSB library. Compiler and tools
  are isolated under local `tmp/pico-adapter-build/`, not the live rig environment.
- Firmware compiled successfully: 79,328 bytes program / 16,880 bytes global RAM.
  UF2 SHA-256: `93f3241518c97104267cabf3ab33c9a4c8e85d701097459e050bd7f05b4b68b7`.
  Local and rig hashes matched; `picotool load -v` completed flash verification.
- USB product `TrueSkate Pico Mouse Test`, development VID/PID `239a:cafe`,
  mouse usage page 1 / usage 2. The rig's IORegistry shows one USB HID interface,
  and macOS attaches its USB HID mouse/event drivers.
- After an eight-second lead, one hover test sends 80 relative moves at least
  40 ms apart, followed by a neutral report. The test never presses a button.
  It has a five-second movement budget and does not replay after host loss or
  after completing. A physical power cycle permits one new run.
- The host cursor observer captured 360 irregular samples across 67.10 s;
  `CGEventCreate` blocking made sampling slower than the intended 50 ms cadence.
  Twenty samples changed position, from 8.61 through 11.71 s. The cursor spanned
  46.58 px in x and y. The starting cursor was near the screen's lower edge, so
  boundary clipping prevents using net displacement as a calibration result.
  No further movement occurred during the remainder of the observation.

This establishes firmware upload, host enumeration and USB mouse movement on
macOS. It does not establish XR2 acceptance, touch/gameplay delivery, pointer gain,
1 ms timing, press/lift preservation or a controllable gesture executor.

## XR2 check

The operator requested screen recording instead of watching the test. XR2 was
temporarily reconnected by its ordinary USB data cable. CoreDevice reported it
paired, booted, with developer mode and DDI services available. The existing rig
service monitor launched its prebuilt WDA automatically; the agent did not
restart or rebuild WDA. Both rig port 8103 and phone Wi-Fi address
`172.19.188.135:8100` then returned ready status. A diagnostic Appium session
successfully attached using that phone Wi-Fi URL, with no app launch or gestures.
These checks retained USB and did not establish USB-disconnect survival.

The root RemoteXPC tunnel was running. WDA reported no active recorder, and the
supported attachment dry run found zero UUID-shaped attachments. The operator
was asked to reconnect the powered adapter while leaving the Pico disconnected,
so wireless recording preflight can precede its eight-second startup lead.

Lockdown reported `EnableWifiConnections` absent and `EnableWifiDebugging=false`.
Automatic approval review rejected a proposed change to enable both persistent
settings as outside the approved connection test. No setting was changed; the
existing reachable Wi-Fi WDA path was tested instead.

After the operator reconnected the powered adapter with the Pico disconnected,
XR2 disappeared from both USB and network libimobiledevice lists. Its Wi-Fi DNS
address remained `172.19.188.135`, but WDA port 8100 refused connections and the
prebuilt xcodebuild runner had exited. CoreDevice still knew the paired phone,
but reported its tunnel unavailable and DDI services unavailable. Attachment
listing failed with device-not-found. This is a wireless debugging/recording
transport failure, not evidence of Pico or adapter USB incompatibility. No
recorder start was attempted. The operator was asked to approve temporary
wireless settings with restoration after the test, or use built-in iPhone
recording instead. The operator subsequently approved both settings, including
retaining them if useful for the design, or restoring them if the test fails or
they are unnecessary. No collector was started.

After USB reconnection, the prior values were saved to `wifi-settings.json`.
`EnableWifiConnections=true` was accepted and read back. XR2 then advertised its
known `_apple-mobdev2._tcp` instance on the Wi-Fi interface as well as USB.
`EnableWifiDebugging` remained false; its setter returned lockdown's
`MISSING_VALUE` (-12), including after the helper was corrected. The initial
ctypes helper mistakenly freed a plist node consumed by `lockdownd_set_value`,
crashing the helper after its first accepted setting. The corrected helper
respects that ownership contract. No phone firmware or WDA build changed.
After the next USB disconnect, WDA again refused connections and CoreDevice's
tunnel and DDI became unavailable. The accepted connection setting alone did
not establish a working wireless developer connection.

A subsequent registry check found the root tunnel daemon still running but with
zero active tunnels, even with XR2 reconnected by USB. Its log records forwarder
loss for both disconnected phones. Installed `tunnel-creation` disables retries
unless an explicit retry option is supplied. A running daemon alone therefore
does not prove a live tunnel after this cable-swap sequence. Its admin restart
needs host administrator authentication; passwordless sudo is unavailable.
The diagnostic recorder now also requires a live XR2 registry entry before any
start, in addition to attachment listing and the running-daemon check.

## Collection design implications (proposal, not a deployed workflow)

With XR2 on the adapter, its classic lockdown TCP port 62078 is reachable at
`172.19.188.135`. The phone's Wi-Fi link-local IPv6 address times out from the
rig's Wi-Fi interface. The rig's IPv4 address is `172.19.194.175`. This
supports a network-path hypothesis; it does not identify a specific campus
firewall rule. An in-memory use of the rig's existing pair record established a
TLS lockdown session over IPv4 and returned the expected XR2 UDID. It did not
launch WDA, establish a recording tunnel, or retrieve a movie. The initial
public-value query returned a repeated value: the installed Node PlistService
adds a second splitter-to-decoder pipe on TLS upgrade. Removing the existing
pipe on this temporary client instance before the upgrade fixed the duplicate
response, and both the expected UDID and iOS 18.7.10 were read correctly.
Pairing secrets were not printed or copied to experiment artifacts.

The operator rejected manual local screen recording as the intended design.
The operator subsequently confirmed that USB data hub, Ethernet adapters and
network hardware are available near the rig. Their models and a private-network
topology remain to be identified; none has been connected or validated here.
Actual collection would retain native XCTest capture and automatic retrieval:

- Rig -> ESP32 bridge -> UART -> Pico -> USB mouse -> powered adapter -> XR2.
  A buffered, clocked Pico gesture executor and acknowledgements still need to
  replace the current single hover diagnostic. ESP32 Wi-Fi can carry commands,
  but rig USB serial to that bridge can serve the same purpose.
- XR2 -> working private IP network -> rig carries WDA control, RemoteXPC,
  movie retrieval and attachment cleanup. A shared network with working IPv6
  is the ordinary Xcode route. A powered USB hub plus supported USB Ethernet
  adapter is another proposed route; compatibility with this third-party
  camera adapter and cumulative power demand remain untested.
- Each segment stays one minute: start capture, bracket the Pico-controlled
  gestures with observed timing controls, stop, retrieve, decode/count frames,
  verify attachment cleanup, then align and admit clips using existing guards.

XCTest records on the phone. Changing its control/retrieval transport does not
intrinsically change the requested capture rate or full-screen geometry. The
current collector requests 30 fps; previous XR2 diagnostics demonstrated
828x1792 H.264 at approximately 59.3-59.65 effective fps when requesting 60.
Those are prior USB-backed results, not validation of this adapter/network
configuration. Network transfer time affects collection throughput and must
be measured separately from source frame cadence. Source PTS remain authoritative.

Model 1 labels cannot use WDA `submitted_to_ios` as the timestamp of a Pico
gesture. The new executor needs report/button-edge logs, calibrated cursor
position/gain, and a Pico-clock-to-video mapping with two controls per segment.
The timing controls must execute through the Pico so their observed frames
calibrate the same clock and input path as the collected gestures. Complete
gesture schedules should be buffered before execution; Wi-Fi packet arrival
must not pace individual mouse reports.
Report acceptance alone is not observed iOS contact. Revalidate press, separate
lift and endpoint behavior before admitting training data. The current fixed
32-frame Model 1 loader does not automatically gain temporal samples from 60-fps
capture; any sampling change is a separate model/recipe decision.

The proposed go/no-go sequence is first a no-USB native recording lifecycle
(start, stop, pull, exact decode/PTS checks and verified attachment cleanup),
then simultaneous HID input and recording. Sustained collection is not
authorized by this maintenance task. Requested 30/60 fps, observed source
cadence and retrieval dead time must be reported separately. The earlier
3.23 MB/s transfer measurement was rig-to-laptop, not phone-to-rig, and is not a
benchmark of the proposed recording transport.

Sources: [Apple network pairing](https://developer.apple.com/documentation/xcode/pairing-your-devices-with-your-mac),
[Appium native capture](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/#mobile-startxctestscreenrecording),
[Apple USB hubs/Ethernet](https://support.apple.com/en-au/111811),
and [existing XR2 rate measurements](HID-REVIEW-20261004.md).

The firmware test sends no clicks or touches. A final solid Pico LED means
TinyUSB accepted reports, not that the phone rendered a cursor. Screen evidence
must establish XR2 mouse acceptance independently.
