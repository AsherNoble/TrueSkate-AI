# HID-USB-20261006 — Powered Lightning adapter and Pico mouse smoke test

Status: XR2 accepted Pico hover, a tap and two drags through the powered camera
adapter during Wi-Fi-controlled XCTest recording (run-09 on 2026-10-07;
run-11 on 2026-10-08). Run-11 supports 3 ms report throughput, but shows no
clear 15 ms jitter improvement over Bluetooth and does not establish clean
1 ms contact timing. No host command link, collection or training.

## Collection design implications (proposal, not a deployed workflow)

With XR2 on the adapter, its classic lockdown TCP port 62078 is reachable at
`172.19.188.135`. The phone's Wi-Fi link-local IPv6 address times out from the
rig's Wi-Fi interface. The rig's IPv4 address is `172.19.194.175`. This
supports a network-path hypothesis; it does not identify a specific campus
firewall rule. An in-memory use of the rig's existing pair record established a
TLS lockdown session over IPv4 and returned the expected XR2 UDID. It did not
launch WDA, establish a recording tunnel, or retrieve a movie. The initial
public-value query returned a repeated value: the installed Node PlistService
adds a second splitter-to-decoder pipe on TLS upgrade. Removing the existing
pipe on this temporary client instance before the upgrade fixed the duplicate
response, and both the expected UDID and iOS 18.7.10 were read correctly.
Pairing secrets were not printed or copied to experiment artifacts.

The operator rejected manual local screen recording as the intended design.
The operator clarified the inventory: the hub is a Simplecom CHU810 powered
10-port USB data hub; Ethernet cables are available, but Ethernet adapters and a
spare router are not. A Raspberry Pi 3 B+ might be available. The earlier
multiple-choice answer suggesting adapters were available was superseded by
this clarification. The manufacturer's manual says both blue and red ports
carry USB data; red ports additionally support BC 1.2 charging. Whether this
hub currently serves the rig's other USB devices was initially unclear. The
operator subsequently confirmed it is the rig's data hub; its upstream must
remain with the rig to preserve those devices.
Actual collection would retain native XCTest capture and automatic retrieval:

- Rig -> ESP32 bridge -> UART -> Pico -> USB mouse -> powered adapter -> XR2.
  A buffered, clocked Pico gesture executor and acknowledgements still need to
  replace the current single hover diagnostic. ESP32 Wi-Fi can carry commands,
  but rig USB serial to that bridge can serve the same purpose.
- XR2 -> working private IP network -> rig carries WDA control, RemoteXPC,
  movie retrieval and attachment cleanup. A shared network with working IPv6
  is the ordinary Xcode route. A powered USB hub plus supported USB Ethernet
  adapter is another proposed route; compatibility with this third-party
  camera adapter and cumulative power demand remain untested.
- Each segment stays one minute: start capture, bracket the Pico-controlled
  gestures with observed timing controls, stop, retrieve, decode/count frames,
  verify attachment cleanup, then align and admit clips using existing guards.

XCTest records on the phone. Changing its control/retrieval transport does not
intrinsically change the requested capture rate or full-screen geometry. The
current collector requests 30 fps; previous XR2 diagnostics demonstrated
828x1792 H.264 at approximately 59.3-59.65 effective fps when requesting 60.
Those are prior USB-backed results, not validation of this adapter/network
configuration. Network transfer time affects collection throughput and must
be measured separately from source frame cadence. Source PTS remain authoritative.

Model 1 labels cannot use WDA `submitted_to_ios` as the timestamp of a Pico
gesture. The new executor needs report/button-edge logs, calibrated cursor
position/gain, and a Pico-clock-to-video mapping with two controls per segment.
The timing controls must execute through the Pico so their observed frames
calibrate the same clock and input path as the collected gestures. Complete
gesture schedules should be buffered before execution; Wi-Fi packet arrival
must not pace individual mouse reports.
Report acceptance alone is not observed iOS contact. Revalidate press, separate
lift and endpoint behavior before admitting training data. The current fixed
32-frame Model 1 loader does not automatically gain temporal samples from 60-fps
capture; any sampling change is a separate model/recipe decision.

The proposed go/no-go sequence is first a no-USB native recording lifecycle
(start, stop, pull, exact decode/PTS checks and verified attachment cleanup),
then simultaneous HID input and recording. Sustained collection is not
authorized by this maintenance task. Requested 30/60 fps, observed source
cadence and retrieval dead time must be reported separately. The earlier
3.23 MB/s transfer measurement was rig-to-laptop, not phone-to-rig, and is not a
benchmark of the proposed recording transport.

### Minimal network proposal after inventory clarification

For the XR2 pilot, a router is not intrinsically required: a compatible USB-A
Ethernet adapter on the phone-side hub can connect directly by the existing
Ethernet cable to a macOS-compatible USB-C Ethernet adapter on the rig. A fresh
read-only check identified the rig as MacBookAir9,1 and found only Wi-Fi and
Thunderbolt interfaces, with no Ethernet adapter currently present. The rig
would retain UTS Wi-Fi for remote access and use a separate private Ethernet
link for phone recording traffic. Local address configuration must preserve
the rig's current Internet/default route and provide working IPv6/mDNS. Apple
documents direct Ethernet links and camera-adapter Ethernet support separately;
this combined XR2/WDA/RemoteXPC topology is an engineering proposal pending
hardware validation, not a proven setup.

The CHU810's upstream cable must terminate at the camera adapter when it serves
XR2; it cannot simultaneously serve the rig as another USB host. If it is
already the rig's data hub, a separate phone-side data hub or a verified
two-port camera adapter would be needed to preserve the rig's other devices.
A second USB socket alone does not establish a recording network.

Further bounded IPv4 probes found a potentially cheaper software route. Reading
the installed RemoteXPC 5.6.2 source identified the exact service name
`com.apple.internal.devicecompute.CoreDeviceProxy`. The earlier guessed
`com.apple.internal.dt.coredeviceproxy` was incorrect; its `InvalidService`
response is not evidence that the actual developer proxy is unavailable over
Wi-Fi. The first corrected helper included a null EscrowBag and failed locally
with TypeError while preparing its StartService request. Omitting that optional
field allowed the correct service to start and return a
port with `EnableServiceSSL=true`. A separate probe then connected to the
service over the phone's Wi-Fi IPv4 address and completed client-certificate
TLS 1.2 using the existing pair record in memory. All client sockets/sessions
were closed; no recording, native tunnel or WDA runner was created.

This establishes reachable developer-proxy TLS without the ordinary USB cable,
not a working recording path. A bounded native `devicectl` details query by the
phone's known DNS name still failed. Installed RemoteXPC/TUN-TAP tooling requires
administrator privileges to create its network interface, and the normal root
daemon currently has zero registered tunnels. A no-purchase IPv4 route remains
worth pursuing before buying Ethernet hardware, but it still needs tunnel
integration, WDA launch and full recording/retrieval/cleanup validation.

A Pi 3 B+ can instead host a private Wi-Fi access point, with its Ethernet port
linked to the rig through one rig-side adapter. This avoids phone-side Ethernet
but adds Pi OS, storage, power and network setup. The private Wi-Fi and Ethernet
must form a working local network for IPv6 discovery; default routed hotspot
settings should not be assumed sufficient. It need not share UTS Internet for
local native recording. A multi-phone wired deployment can add an Ethernet
switch and a phone-side adapter per XR; a router is still optional for this
local recording network. No hardware purchase or network configuration was
performed.
