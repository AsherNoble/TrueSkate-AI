## The Orange Finger-Trace Is Real, Distinctive, and Transient

- Confirmed visually: a 360-flip frame (`360_single_flip_001/img_00010.jpg`) shows a bright **orange swoosh** trailing the flick — the finger-trace True Skate renders. It's the signal Model 1 reads.
- **Transient:** present only during/just after an active drag; mid-air/settled frames have no trace (already faded). Labeling must align frames to when the touch is active.

## Conclusion → Why Asher's Agent-as-Labeler Is the Right Move

- The trace exists and the extractor *fires*, but its **positional accuracy is unknown** and the hand-tuned HSV+temporal heuristic clearly mislabels in places. There is no ground truth to validate or train against — until we make some.
- **The agent generates touches it knows exactly.** Capture clean screen frames during agent gestures → `(frame, known-touch)` is free ground truth. Use it to (a) **measure** trace_extractor's true positional error, and (b) **train Model 1** (a learned extractor that beats the heuristic). This is the unblocking step for the whole leap.
- **Prerequisite that wasn't obvious:** the corpus must be **color, full-frame screen captures** (like `data/extracted_frames`, or AVFoundation USB capture) — NOT the grayscale 210×455 RL frames and NOT the external hand-clips. The Stage-1 capture must save color screen frames.

## On-Device Self-Labeling — VALIDATED (2026-06-14, iPhone_XR)

Brought WDA+Appium up (directly, no launcher monitor — see ops note) and ran the new `collect_self_labeled_traces.py`. Color MJPEG capture works: full-res **1792×828 RGB** frames with per-frame timestamps. Findings from ~140 collected gestures:

1. **The trace only renders for on-board FLICKS, not arbitrary drags.** Random screen drags in empty space produce no trace and don't move the board (`warm@label=0`). Fixed the sampler to start on the board (~x∈[0.38,0.62], y∈[0.50,0.80]) and flick outward — every such flick produces a trace (50/50). (Some flicks even land real tricks, e.g. a BACKSIDE 180.)
2. **The orange trace LAGS the flick by ~0.4-0.5s.** The swoosh peaks a median **+0.33s after the gesture END** (50/50 samples, range +0.14..+0.66s) — it's a lingering render of the completed flick path, not coincident with the finger. My first instantaneous-point labeling therefore marked the trace-rich frames "inactive."
3. **Latency-shifted labels align with the trace.** Sweeping `latency_s`: at 0.0s only **1%** of active-frame labels land on the trace; at **0.40s → 78%**, at **0.50s → 85%** (median warm-px at label jumps 0 → ~2000). **`latency_s ≈ 0.45` is the validated offset** — now the default in `train_trace_extractor.py` + a trace-presence gate keeps only aligned frames.

**Conclusion: Asher's agent-as-labeler approach WORKS on-device.** Clean color frames + known flicks + a ~0.45s latency shift → a corpus where labels sit on the rendered trace ~80% of the time. The label naturally lands at the flick's end (swoosh head). For Model 2 the richer target is the whole flick *path* the swoosh encodes (refinement). Corpora on disk: `data/self_labeled_traces/iPhone_XR_20260614_011235` (50, board-flick) + `..._011856` (250) — gitignored under /data/.

## SLS Sequence-Data Collection + the Clapperboard Latency Result (2026-06-16)

Built the **SLS random-gesture trace collector** (`scripts/data/collect_sls_traces.py`) — the missing half of the sequence-model corpus. CMA-ES trick mining must stay on the single-reset flatground park (obstacles + multi-reset contaminate params), so SLS arenas are used ONLY to collect `(frame, known-gesture)` pairs. It is **obstacle-tolerant**: the executed gesture is the label, so wall-bumps / whiffs / varied board positions are *desirable diversity*, not contamination. Mixture sampler (`data/gesture_sampling.py`): **60% board-flicks / 25% full-random N-slot vectors / 15% perturbed library recipes** (`recipe_to_vector` round-trips exactly through `unpack_gesture_params`). Per-sample meta carries the gesture (label), park, `frame_times`, and the capture offset.

**The clapperboard (frame↔gesture latency) — the load-bearing result.** Goal: Δ, the command→frame pipeline lag, so a frame pairs to the right point in the gesture timeline. The dead-ends and the answer:
- **Reset-snap via the board localizer FAILED.** On a reset the board *vanishes* from the localizer for a variable ~0.1–0.4s (reset animation) then reappears at home ~0.45s later — no crisp onset; board-centroid Δ swung **0.067 → 0.49s** (jitter 0.20). Anchoring to the settled-home position rejected the localizer's spurious mid-transition jumps but yielded too few clean samples.
- **No in-game visual is instant.** True Skate animates everything: the `•••` menu ramps over ~0.3s, SETTINGS over ~1.0s. So the sync event can't be a True Skate element.
- **Solution — a dedicated Clapperboard app** (`github.com/AsherNoble/Clapperboard`, a SwiftUI full-screen black↔white toggle that flips in ONE frame, animations disabled). The rig `activate_app`s it, taps to flip, times the flip in the MJPEG, returns to True Skate.
- **KEY INSIGHT — anchor to the COMMAND CALL-RETURN, not its issue time.** Appium's synchronous tap has ~**0.85s of command overhead BEFORE the effect** (variable ±0.1s), but the flip reliably appears **~0.07s BEFORE the call returns**. Flip-vs-issue jitters ±0.1s; **flip-vs-return is −0.037s ± 0.027s (sub-frame)**. So `Δ = flip_frame_time − command_call_return`, and each sample's `frame_times` are anchored to the gesture call-return (`gesture_end_monotonic`); the on-screen gesture spans `frame_times [Δ − duration, Δ]`. Device-verified: **n=14/14, Δ −0.037s, MAD 0.027s**.
- **Δ is ~constant per session → calibrate once at startup** (not per-eval), which is why the app-switch is affordable. MJPEG ~10–15fps floors per-frame precision at ~0.07–0.1s anyway; our offset jitter is already under that.
- **Apple Dev account:** free signing expires every **7 days** (the weekly WDA re-sign pain); paid **$99/yr → ~1 year**, fixing it for WDA *and* the Clapperboard app.

**Park rotation — rudimentary ntfy tap-to-confirm (vision detector rejected).** A first attempt (a vision diverge-then-resettle `park_change` detector) was brittle and scrapped. Now: on the per-park timer the collector sends a **"switch park" notification with a tappable `http` action button**; tapping "I switched parks" POSTs to a derived ntfy **control topic** (`<topic>_ctl`) that the collector polls; on receipt it advances the park label + resets the timer. It keeps collecting in the current park until you tap (no idle time when away); a plain "done"/"switched" message typed to the topic also works. Device-verified end-to-end on the iPhone 11 (samples re-tagged to the new park after one tap). Gotcha logged: an emoji in an HTTP header (latin-1) broke the whole notification — `notify` now sanitizes header values.

## Capture Frame-Rate: WDA MJPEG vs AVFoundation/DAL — the 30fps Wall (2026-06-22)
- **Why this matters:** inference-time screen recordings are **60fps**; the SLS corpus is captured via WDA's MJPEG at **~10–15fps, variable**. That's a train/inference *distribution* gap (per-frame motion magnitude, blur, trajectory smoothness all differ for a sequence model), not just a label-precision issue. Also the label floor = 1/fps, so low fps dominates the gesture↔frame error budget (clapperboard jitter MAD 27ms already sits under it).
- **WDA MJPEG is a dead end for 60fps** — it's screenshot-re-encode on the device CPU (A12), inherently variable; bumping `mjpegServerFramerate` would get ~15–25 variable fps at best. Not pursued.
- **Prototyped the AVFoundation/CoreMediaIO DAL path** (the `scripts/view_device.py` front-end — same H.264-over-USB pipeline QuickTime uses; ffmpeg sees the phone only via the `tools/enable_dal.c` DYLD shim). Measured on **iPhone_XR (Test XR_1)**, ffmpeg `-f null` frame counts over 10–15s:
  - Default mode = **1920×1440@30** (4:3) → steady **30.0 fps** (450 frames / 15.0s).
  - Device *advertises* 60fps modes, but only at 16:9 (640×480 / 1280×720 / 1920×1080); the 4:3 max-res mode is 30-only.
  - Requested 60 at **1920×1080 → 30.0 fps** (450/15s); at **1280×720 → 30.0 fps** (300/10s). `speed=1x`, identical across resolutions ⇒ **not** a Mac-side/bandwidth bottleneck. **The DAL screen-mirror stream is hard-capped at 30fps on this XR** — the advertised 60fps formats are camera descriptors the mirror pipeline doesn't actually fill.
- **The one real win:** DAL is **rock-steady 30.0** (frame counts exactly linear) vs MJPEG's variable ~10–15. So DAL fixes the *variability* but delivers *half* the target rate. Still short of 60fps inference.
- **Operational gotchas (carry into any DAL integration):**
  - **AVFoundation device indices REORDER between calls** (Test XR_1 was `[2]` then `[1]`; FaceTime/phones shuffle). Addressing by index opens the WRONG device → **always reference by exact NAME** (`-i "Test XR_1"`).
  - DAL device is **exclusive + fragile**: repeated open/close cycling produced intermittent then persistent `Input/output error` (the documented CMIO wedge, memory `ios-dal-screen-capture-wedge`). Fix = QuickTime New Movie Recording re-activate, or replug; CMIO/usbmuxd restart does NOT help.
  - Capture modes are 4:3 / 16:9, **none match the phone's ~2.16:1 screen** → a DAL frame letterboxes/pillarboxes the game, a *framing* mismatch vs native screen recordings (favors on-device capture for distribution match). [unverified by eyeball — frame grab failed on the wedge]
- **Decision pending (Asher):** B = ship DAL at **steady 30fps** (accept half-rate, gain steadiness + likely temporally-interpolate to 60 offline), vs C = **on-device ReplayKit 60fps recording** + offline alignment via an in-frame timecode (true 60fps + native framing, but loses the live monotonic-clock sync — more engineering). **60fps is only reachable via C on this hardware.**
- **Drag-vs-tap Δ check is DEFERRED** until the capture path is chosen — it must run on the pipeline we actually ship (its latency Δ is pipeline-specific), not the about-to-change MJPEG path.

## DAL FREEZES Silently — the Scary Failure Mode (2026-06-23, ~1am, chosen path D then bed)
- **Δ_MJPEG measured (clapperboard over MJPEG): +0.034s, MAD 0.016s, n=12** — consistent with the drag-vs-tap tap value (+0.023s). Small positive, ~1 frame at 30fps. (The MJPEG pipeline is fine; this is the cross-pipeline base.)
- **Cross-pipeline gap G BLOCKED — the DAL stream FROZE.** Over 10 board resets: MJPEG saw the snap clearly every time (**~13–15% of pixels change, onset ~0.31s, peak ~0.62s**), but **DAL showed 0.0% change across 43–45 frames** — every frame bitwise-identical. The reset is real (MJPEG proves it); DAL was delivering frozen duplicates.
- **The dangerous part — the freeze is SILENT to a naive watchdog.** When the CMIO/DAL session stalls, ffmpeg's `-vf fps=30` pads the output with bitwise-identical duplicate frames. So `frame_count` keeps climbing, `last_frame_age` stays ~0, `is_alive()` stays True — yet the content is frozen. A collector trusting frame-arrival would **silently save frozen frames labelled with gestures → a corrupted corpus**. A *fresh* ffmpeg open shows live content (mean_lum 92.8), so it's the persistent session that wedges, almost certainly triggered by the night's app-switching (True Skate ↔ Clapperboard for calibration). Same CMIO wedge family as memory `ios-dal-screen-capture-wedge`.
- **FIX (made, UNTESTED on-device — DAL wedged before I could verify):** `DalFrameRecorder` now tracks `content_stale_age` (subsampled exact-equality → time since decoded content last *changed*). Collector: (1) startup **liveness check** — force a push+reset, confirm content moved, else fail with the wedge hint; (2) in-loop health check restarts on `content_stale_age>8s` then forces a reset and confirms LIVE, else STOPS (a restart can't clear a CMIO wedge, so never collect frozen). Added `--capture-offset-s` to stamp Δ_DAL directly while the DAL clapperboard is blind.
- **Drag-vs-tap — analytical answer (empirical deferred to tomorrow's app fix):** both `mobile: tap` and the W3C drag `perform()` are synchronous and return after the FINAL HID event (the lift) is flushed, so the tap's Δ should anchor the gesture's ENDPOINT (lift) the same way → **LIFT-anchored**. Mid-path positions ride the separate execution-timing-fidelity term (nominal duration/easing on-device), not Δ. Fully **retroactively correctable**: every sample stores raw `frame_times` + the offset, so any Δ revision tomorrow is an offline relabel, no re-collection.
